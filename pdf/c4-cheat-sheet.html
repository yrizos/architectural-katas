C4 Model

Simon Brown created the C4 model and maintains its official site at c4model.com. The model describes a software system as a small set of diagrams, each one zooming further in, much like the zoom levels of a map. It prescribes no shapes or colors, so the notation below is one common convention.

Four levels of zoom

  1. flowchart LR
  P["     "]:::person --> S["Your system"]:::sys --> E["External"]:::ext

    1System Context

    Who uses the system, and what does it depend on?

    Start here, but don't spend too much time.

  2. flowchart LR
  P["     "]:::person
  subgraph B["Your system"]
    A["App"] --> S["Service"]
    S --> D[("Data")]
  end
  P --> A
  class B boundary

    2Containers

    What are the main building blocks, and how do they communicate?

    This is what you present. Start with containers and name each technology by its category, such as relational database, rather than by vendor.

  3. flowchart LR
  A["App"]
  subgraph B["Service"]
    C1["Component"]:::comp --> C2["Component"]:::comp
  end
  A --> C1
  C2 --> D[("Data")]
  class B boundary

    3Components

    How is one container organized inside?

    Also what you present. Draw it only for the container that carries your most important decision.

  4. classDiagram
  direction TB
  class A["Class"]
  class B["Class "]
  class C["Class  "]
  A <|-- C
  B <|-- C

    4Code

    How is a component implemented?

    Skip it in the kata.

Tips

  • Give each diagram a title and a key for your shapes and lines.
  • Label every arrow with what it does. An unlabeled arrow hides a decision.
  • Draw each arrow in one direction and make its label read the same way.
  • Show build or buy on the element itself, as in [Container: managed relational database].
  • Mark each key decision on the diagram with its number from the decisions log.

The component diagram zooms into the API container from the previous page. Its components group related responsibilities behind clear interfaces, and all of them deploy together as one service.

Follow one request

  1. 1The Mobile app syncs a learner's progress to the Request gateway.
  2. 2The gateway verifies the token with the Identity provider.
  3. 3It routes the request to Progress tracking.
  4. 4Progress tracking reads and writes the Database.
  5. 5It publishes the completion to the Message broker.
